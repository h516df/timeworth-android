# 从用户目标到可用交付

规则 0.4。代理执行本流程，用户无需填写技术表格。它约束“何时可以报告完成”，不新增发布权限或要求用户重复授权。

## 先确定用户要收到什么

开工时从当前指令、项目约定和已有渠道整理 2–5 条完成条件：交付位置、发行级别、实际可用产物、下载者访问条件、验收方式。已有明确目标时直接执行，不让用户重复选择。

- 用户在 GitHub 项目中要求安装使用，先查项目既有下载渠道；不能把一个新建的 Page、源码 ZIP 或仓库内文件链接默认为最终安装包交付。
- 用户指定正式 GitHub 发行时，完成条件包含非草稿、非预发行、所需原生附件和正确的最新版本入口。仅改标题、发布说明或构建包名不能满足这些条件。
- 调试包、原签名非调试包、GitHub 正式发行、公开自动更新渠道、实体设备安装分别记录。诚实披露未测项目，不擅自把全部未来功能或所有设备验收变成用户未要求的发行前置条件。明确的用户指令优先；签名、访问范围和数据保护仍按现有授权处理。
- 默认不更改仓库可见性、收费、长期签名或其他应用的更新入口。无法完成用户指定目标时保留可用成果、准确说明剩余缺口，不能把替代产物写成目标已完成。

## 先做廉价预检，再做昂贵工作

识别当前云端已有工具及其真实能力：Java 同时核对 `java` 和 `javac`，构建工具核对实际版本/可执行路径，SDK 核对要求的平台和 build-tools。区分已验证缓存、可重新下载的依赖和必须配置的 Secret。不要把 JRE 当 JDK，也不要无条件重新下载已有的相同构建工具。

使用正常的工具链/凭据选择机制，不打印环境、私钥、密码、令牌或临时签名下载 URL。预检不为“证明权限”创建测试仓库、改变收费或重建签名。涉及工作流文件先做语义校验；自托管标签需显式提供给校验器。

## 按失败所在层定位

| 观察 | 还不能得出的结论 | 下一步 |
| --- | --- | --- |
| 托管 Actions 因付款/额度在步骤前拒绝 | 必须付费才能使用仓库、Release，或本项目无法构建 | 保留原报错；账单无权限则原因未细分。检查已授权云端独立构建/一次性自托管是否可用，不调整预算、不盲目重跑同一路径 |
| 某连接 401/403 | 所有已有连接都不可用，或需要用户重新授权整套工作流 | 区分服务、主机、端点、令牌作用域与执行环境。复用适合此操作的既有官方授权；不可绕过权限、代理策略或提取令牌 |
| Release 创建成功、附件上传失败 | 发布能力已全部验证 | 分别核对 API 主机和附件上传主机；能创建草稿不等于能上传原生附件。可在已授权的一次性 Actions 作业中正常使用作业令牌发布，不把令牌带出作业 |
| 下载工具/编译器阶段失败 | 应用代码测试失败，或原签名有问题 | 定位到实际失败命令，再选择已验证版本、正确 JDK 或缓存；相关预检通过后才重试 |

复用当前云端的一次性 self-hosted runner 时，仅绑定目标私有仓库、专用标签和已核对的源码；设置超时，单作业退出并回读移除结果。编译和上传按所需最小权限拆开，上传不需要签名私钥。不能因此引入新的收费服务、把私有源码改公开、运行不可信 PR 或把临时机器当永久服务。GitHub 的自托管政策与权限以当前官方文档及实际响应为准。

## 发布与回读是一项完整工作

1. 从 Git/API 读取真实完整 SHA，不手写、猜测或补齐提交号。记录应用构建 SHA、发布标签 SHA及文档后续提交；不同 SHA 之间以源码/产物内容匹配说明关系。
2. 在既有授权内创建草稿、上传用户需要的原生附件。上传失败不提前结批或报告“可下载”；中间文件仅标为中间成果。
3. 逐个核对附件名、`state=uploaded`、字节数、SHA256 和对应版本的 HTTPS 下载地址；源码归档或说明中的仓库文件链接不能冒充原生附件。
4. 按用户要求发布为正式版或预发行。正式版回读 `draft=false`、`prerelease=false`；要求最新时，`/releases/latest` 必须指向此 Release。不要只看发布命令退出码。
5. 从最终记录取得用户入口；核对需要登录还是匿名可用。实际客户端下载安装若未执行，明确未执行，不能把 API 摘要核对说成真机或匿名下载通过。
6. 完成临时凭据/runner 清理，更新当前交接、配置和回执后才报告完成。恢复方案、公开更新清单的切换按项目范围独立处理。

## 可执行的 GitHub 发布核验

`scripts/verify_release.py` 仅通过现有 `gh api` 做只读请求，不创建/发布 Release、不接触签名或付款设置。新接入项目复制到 `cloud/verify_release.py`。契约由代理维护，例如：

```json
{
  "schema_version": 1,
  "repository": "owner/project",
  "tag": "v1.0.0",
  "kind": "release",
  "require_latest": true,
  "target_commit": "替换为从 Git/API 读取的完整40位SHA",
  "assets": [{
    "name": "app.apk",
    "size": 12345,
    "sha256": "替换为已验证产物的真实64位SHA256"
  }]
}
```

这是带占位符的示意，不是可用发布证据。`kind` 也可明确为 `prerelease`，此时不要求 GitHub latest。每项可加项目根内的 `path`，额外核对本地文件；不要求把二进制复制进只有工作流的分支。

```bash
python3 cloud/verify_release.py --contract release/delivery-contract.json --receipt /tmp/release-receipt.json
```

以本次命令退出码 **0** 和本次 `status=verified` 回执为成功；失败退出非零，并把指定回执更新为失败，防止重用旧成功。契约、时间戳、标签、发布级别、来源提交和附件摘要必须对得上。脚本验证的是 GitHub 状态/元数据和已固定摘要，不验证签名、客户端匿名下载或设备安装；这些继续使用项目对应检查。

## 少返工，少让用户催促

- 同一目标的纠正优先续当前未结束的任务/PR；按协调协议续租、扩范围和重验。不要每修正一句交付说明就新建一套批次、分支、预发行。已完成/冻结的任务按协议接续，不能回写或绕过其他写手的占用。
- 关键检查失败即停止依赖操作；shell 使用失败即停或显式判断退出码，不能因为最后一条命令成功就忽略前面的检查失败。测试/构建/发布/提交依赖按顺序执行。
- 用户纠正发布状态时检查所有完成条件，不只修正最后一句话；由代理完成回读，不把用户截图当唯一发布验收。
- README 当前状态、活动交接和当前配置保持一致，过期规划移到有标题的历史区。回执写明实际采用/合并的分支；未合并到默认入口不能说对所有后续会话已生效。
- 最终先给用户可用入口与实际完成状态，再简述必要限制。账户级生效、后台永久运行和平台权限只能依据实际配置确认，不能靠 GitHub 文档存档承诺。
